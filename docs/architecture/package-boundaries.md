# Package Boundaries

本文档冻结 Caelush V1 当前的工程边界。Phase 1 已正式落地 Protocol Contract 与 Core 的 Run State Machine，Phase 2 已正式落地 Storage 与 Events 的持久化/消费边界；其余职责仍是后续阶段的边界，不代表对应功能已经实现。

通用规则：

- 所有 package/app 都是 private ESM workspace project。
- 所有公共 API 从 `src/index.ts` 导出；workspace 开发可直接解析这个入口，Node package 构建仍生成 `dist/`，禁止深层 `src` import。
- app 只能向下依赖 package；package 绝不依赖 app。
- 内部 package 依赖使用 `@caelush/*` 包名与 `workspace:*` 协议。
- `protocol` 位于最底层，只承载跨边界 Contract，不依赖其他 Caelush feature package；当前唯一真实的内部依赖是 `core → protocol`。
- `shared` 只承载真正跨模块、无业务含义的通用工具；“暂时不知道放哪”不是放入 shared 的理由。

## Boundary intent

Phase 1 已正式化 `protocol` 中的 Contract，并由 Core 的状态机通过公共入口消费它；Phase 2 通过 `events → protocol` 与 `storage → events + protocol` 接入持久化和事件消费。Phase 5C 允许 `context → @caelush/llm/messages` 复用 provider-independent message contract，但不允许 Context 触达 LLM runtime 或 provider adapter。Phase 7B 允许 `storage → tools` 作为 ToolExecutionStore 的 adapter 方向，但 `tools` 仍只依赖 Protocol 与既有 Ajv schema runtime，不能反向依赖 Storage、Events、Runtime、Security 或宿主。Phase 9A 反转 Gate 依赖：`tools` 只定义 `ToolExecutionGatePort`，`security` 实现它；`tools` 绝不依赖 `security`。`events` 只拥有 port，不反向依赖 `storage`；`storage` 保存 Protocol entity、Durable Event 和 Tool lifecycle projection，但不执行具体 Tool。保持边界现在就可验证，可以避免后续把 CLI/Web 逻辑、provider 细节或执行权限渗入 Kernel。
