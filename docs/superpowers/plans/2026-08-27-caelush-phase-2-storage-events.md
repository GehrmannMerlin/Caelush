# Caelush Phase 2 Storage & EventBus Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Phase 2 durable SQLite storage and replayable EventBus foundation while preserving the Phase 1 protocol/state boundaries and explicitly excluding AgentLoop, runtime execution, HTTP, CLI, and Web features.

**Architecture:** `@caelush/events` owns the provider-neutral DurableEventStore port, typed draft, EventBus fan-out, and replay/live watch contract; it depends only on `@caelush/protocol`. `@caelush/storage` owns the explicit-path SQLite lifecycle, Drizzle schema/migrations, protocol codec, repositories, and the SQLite EventStore implementation; it depends on `@caelush/events` and `@caelush/protocol`. SQLite is the durable source for Session/Run/Step/State snapshots and durable event history, while ephemeral events remain process-local.

**Tech Stack:** Node.js 24.18.0 `node:sqlite`/`DatabaseSync`, TypeScript ESM, Drizzle ORM `1.0.0-rc.4`, Drizzle Kit `1.0.0-rc.4`, Zod 4 protocol schemas, Vitest, committed SQL migration with Drizzle migration ledger.

## Global Constraints

- Keep dependency direction `events → protocol`, `storage → events + protocol`, and `core → protocol`; never add `events → storage` or `core → storage`.
- Use `node:sqlite`; do not add `better-sqlite3`, `dotenv`, AgentLoop, RunController, LLM, tools, runtime execution, HTTP/SSE, CLI, or Web behavior.
- Pin `drizzle-orm` and `drizzle-kit` to exact `1.0.0-rc.4` versions because the official Node SQLite guide currently documents the RC line; verify the actual API on Node 24.18.0.
- Public Storage APIs are async and accept an explicit database `path`; do not open a database through module import side effects or expose `DatabaseSync`, raw Drizzle handles, or migration internals.
- Persist durable events before publication; ephemeral events are live-only; per-run sequence allocation is transactional and must never use `MAX(aggregate_sequence) + 1`.
- Decode every stored JSON value with its Protocol schema and throw a typed `StorageDecodeError` on invalid JSON, schema drift, or query-column/JSON mismatch.
- Use committed migrations and a migration ledger; database-file existence is never evidence that migrations ran.
- Keep transactions short, use indexed query columns, enable foreign keys, use WAL for file-backed databases, set a 5000ms busy timeout, and do not persist ephemeral stream chunks.
- Follow TDD for each behavior: write one failing test, run it to observe the expected missing-behavior failure, implement the minimum, rerun, then refactor only while green.
- End with fresh `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm format:check`, `pnpm check`, focused Storage/Event/Architecture tests, `PRAGMA integrity_check`, `git diff --check`, and a final status check.
